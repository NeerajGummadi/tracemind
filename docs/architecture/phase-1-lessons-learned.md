# Phase 1 Engineering Lessons Learned

> Retrospective on Milestones A–F: the reactive golden path (Connector Service
> → Kafka → Incident Service → PostgreSQL → Outbox Publisher → Kafka), built
> and validated against real infrastructure throughout, not just unit tests.

## Kafka offsets

Manual acknowledgment (`AckMode.MANUAL`, `enable-auto-commit: false`) is what makes the rest of the design's correctness claims true. Auto-commit would advance the offset on a schedule regardless of whether the message was actually processed — under auto-commit, a crash between "Kafka handed us the message" and "we finished writing to Postgres" would silently lose the message forever (offset already advanced, message never durably handled). With manual ack, `ack.acknowledge()` is the *last* line of the listener, called only after the database transaction has committed (or after a confirmed duplicate). The offset is the single fact that decides "will this message come back." Getting its placement right — after the transaction, not before, and not automatic — is the one design choice that everything else in this system depends on.

The corollary, proven directly in Scenario 6 of the validation report: a consumer that stops committing offsets (because it can't, or because it crashed) doesn't lose data — Kafka just holds the backlog. We watched this happen for real: incident-service's consumer took ~44 seconds to rejoin its group after a Kafka restart, and the alert sent during that window sat safely on `signals.received.v1` and was processed correctly the moment the consumer came back. Nothing was lost. Nothing needed to be.

## Idempotency

One mechanism protects the entire pipeline against duplicate delivery: `signals.event_id UNIQUE`, checked as the literal first statement of the transaction, flushed immediately so the constraint violation (if any) surfaces before any other work happens. Because it's first, a violation is unambiguous — nothing else in that transaction could have produced it — so `DuplicateSignalException` never needs to inspect the exception message or guess at intent. It either means "this exact signal was already fully processed" or it can't happen at all.

This is also why a *deterministic* `eventId` (SHA-256 of Alertmanager's `fingerprint` + `startsAt`, decided back before Milestone C was implemented) matters more than it might look: it means Connector Service's own retries — and Alertmanager's own webhook retries — collapse into the same `event_id` naturally, without Connector Service needing a datastore of its own to detect duplicates. Idempotency is enforced exactly once, in exactly one place, using a mechanism (a database constraint) that can't be bypassed by a bug in application logic the way an in-memory or best-effort check could be.

## Transactional Outbox

The outbox pattern exists to solve one specific problem: a service can't atomically "write to its own database" and "publish to Kafka" as a single operation, because they're two different systems with no shared transaction. Milestone D's `SignalIngestionService` sidesteps this by never talking to Kafka at all during signal ingestion — it writes an `outbox_events` row in the *same* Postgres transaction as everything else, and a completely separate component (`OutboxPublisher`, Milestone E) is the only thing that ever talks to Kafka about `investigation.requested.v1`. The two concerns — "did we decide to request an investigation" and "did we tell Kafka about it" — are fully decoupled, and each is handled by the storage system best suited to it: Postgres for the durable decision, Kafka's own ack protocol for confirming delivery.

The pattern's honest cost, which the blueprint states outright and Milestone F's crash-window documentation makes concrete: there's an unavoidable window between "Kafka accepted the publish" and "Postgres recorded that fact" where a crash produces a duplicate message on `investigation.requested.v1`. The pattern doesn't eliminate duplicates — it makes the *type* of failure something downstream idempotency can absorb, converting "might lose a message" (unacceptable) into "might duplicate a message" (fine, if the consumer is idempotent).

## Correlation

Deterministic correlation (blueprint §4: same environment, same primary service, `status != COMPLETED`, `lastObservedAt` within 5 minutes) turned out to have exactly one behavior worth being careful about: an outbox row must be written *only* when a new incident is created, never when a signal correlates into an existing one. Scenario 3's validation made this concrete — two signals into one incident, but exactly one outbox row, not two. Get this wrong and every correlated signal re-requests an investigation that's already in flight; the blueprint's decision (confirmed explicitly before Milestone D began) to gate the outbox write on `isNewIncident` is what keeps "correlate" and "trigger new work" as genuinely separate concerns.

Severity escalation needed a policy the blueprint doesn't specify (no ordinal ranking of severities exists anywhere in the blueprint text), so Phase 1 defined one: `INFO < WARNING < HIGH < CRITICAL`, escalate-only, documented as a Phase 1 default rather than a blueprint requirement. Validated live in Scenario 5: WARNING → HIGH → CRITICAL escalates at each step, and a trailing WARNING signal afterward leaves the incident at CRITICAL rather than pulling it back down. Monotonic-only severity is a deliberate simplification — a real de-escalation policy (e.g., "no CRITICAL signals in the last N minutes") is a genuine design decision for a later phase, not something to improvise into this milestone.

## PostgreSQL transactions

Two lessons here, both learned the hard way rather than anticipated.

First: Hibernate's dirty-checking and transaction rollback only behave the way you expect if you understand where a failed statement leaves the underlying Postgres session. A failed `INSERT` doesn't just throw a Java exception — Postgres aborts the entire transaction server-side, and no further statement on that connection succeeds until rollback. This is *why* `SignalIngestionService.ingest()` can't catch the duplicate-key exception and keep working in the same transaction (a design temptation that would have been wrong) — the only correct move is to let the whole transaction unwind, which is also the only thing that needed to happen anyway, since a duplicate signal shouldn't trigger any of the correlation logic.

Second: `FOR UPDATE SKIP LOCKED` — the mechanism that makes the Outbox Publisher safe for multiple concurrent instances (or even multiple overlapping poll cycles) without them racing to publish the same row — was deliberately written as literal SQL inside a native query rather than through Hibernate's `@Lock`/`@QueryHints` abstraction. After several unrelated Boot 4/Hibernate 7 API surprises earlier in this same project (see below), trusting an ORM abstraction to translate correctly to `FOR UPDATE SKIP LOCKED` felt like an unnecessary bet; writing the SQL directly removed that uncertainty entirely; it worked on the first try.

A smaller but real finding: `jsonb` columns don't preserve the text you insert — Postgres canonicalizes key order and whitespace on write. A payload-preservation test that compared literal strings failed not because publishing was broken, but because the assertion assumed byte-for-byte round-tripping that `jsonb` was never going to provide. The fix was to compare parsed JSON content, which is what "preserved correctly" actually means.

## Failure recovery

The single idea underlying every failure-recovery decision in this phase: **never acknowledge success you can't guarantee.** Connector Service doesn't return `202` until Kafka has confirmed the publish. Incident Service doesn't commit the Kafka offset until Postgres has committed the transaction. The Outbox Publisher doesn't mark a row `PUBLISHED` until Kafka has confirmed *that* publish. Every one of these is the same pattern applied at a different hop, and every one of them is what makes "at-least-once, never lose a message" true rather than aspirational.

The corresponding failure-mode discipline: bound every wait, and don't retry things that can't succeed on retry. `send-timeout-ms` was meant to bound an entire publish attempt but, as originally configured, only bounded the post-send future — Kafka's own `max.block.ms` (default 60 seconds) governed the pre-send metadata-fetch phase that our timeout never touched. Live validation with a genuinely stopped Kafka broker (not a mocked failure) is what surfaced this — the gap was invisible to unit tests specifically because those tests had their own short `max.block.ms` overrides for speed, which happened to mask the exact production gap they were modeling. The fix (explicitly set `max.block.ms` to match the intended timeout) is a two-line change; finding it required actually stopping Kafka and watching wall-clock time, not reasoning about the code in the abstract.

## Why the design provides at-least-once semantics (and not more, or less)

Every hop in the pipeline follows the same shape: **do the work, wait for confirmation, only then advance the position that controls redelivery.** Connector Service holds off on `202` until Kafka acks. Incident Service holds off on the offset until Postgres commits. The Outbox Publisher holds off on `PUBLISHED` until Kafka acks. At every one of these points, a crash *before* confirmation means the upstream system (Alertmanager retrying the webhook, or Kafka redelivering the message) will try again — nothing is lost. A crash *after* confirmation but before the position update means the same retry happens even though the work already succeeded — that's the duplicate window, and it's why every consumer of every one of these topics has to be idempotent, not just polite about retries.

That's exactly at-least-once: no message is ever silently dropped, and duplicates are structurally possible but always survivable, because idempotency is enforced at the one place that actually matters (`event_id UNIQUE` in Postgres) rather than assumed away. The blueprint explicitly rules out chasing exactly-once (Section 11: "the system does not attempt global exactly-once processing"), and every design choice in this phase — deterministic `eventId`s, the outbox pattern, `FOR UPDATE SKIP LOCKED`, manual offset acknowledgment — is in service of making at-least-once *actually* safe, rather than quietly hoping duplicates don't happen.
